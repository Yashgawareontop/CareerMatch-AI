# Architecture

## Request flow (target)

```
Browser (Next.js client components)
   │  useQuery / useMutation (realtime)            fetch / server actions
   ▼                                                      ▼
Convex (database: users, resumes, analyses,     Next.js server (route handlers)
        jobs, matches, saved items)  ◄──────────  ├─ lib/ai     → Gemini / Groq
                                     ConvexHttp   ├─ lib/resume → PDF/DOCX → text
                                     Client       └─ lib/jobs   → Adzuna, Remotive, …
```

- The client reads data from Convex directly (reactive queries).
- Heavy or secret work (AI prompts, resume parsing, job API calls) runs on the
  Next.js server, which then writes results into Convex through mutations.
- API keys never leave the server (`lib/env.ts` imports `server-only`).

## Resume parsing flow (Phase 2)

1. Browser: `resumes.generateUploadUrl` (rate-limited) → POST the file to
   Convex storage → `resumes.create` (checks size ≤ 5 MB and declared type;
   status `uploaded`).
2. Browser: `POST /api/resume/parse { resumeId }` with the Convex access token
   as `Authorization: Bearer` (the proxy skips `/api/*`, so the cookie token
   may be stale).
3. Route: `resumes.startParsing` runs as the user (ownership check, rate
   limit, status `parsing`, returns an attempt id) → download →
   `parseResume()` checks the real type with `file-type`, extracts with
   `unpdf` / `mammoth` (HTML output, plus page headers/footers), and sends
   near-empty PDFs to Gemini (`GEMINI_OCR_MODEL`, Flash-Lite) →
   `resumes.completeParsing` / `failParsing`. Those two take
   `RESUME_PARSER_SECRET` (set in both `.env.local` and Convex) instead of the
   user token: access tokens live 60 s, and users must not write parsed text.
4. The page shows each status change live via `resumes.listMine`.

## Resume analysis flow (Phase 3)

1. Browser: after a successful parse (or the Analyze button),
   `POST /api/resume/analyze { resumeId }` with the access token.
2. Route: `analyses.start` runs as the user (ownership, resume is parsed, rate
   limit `resumeAnalyze`, no other run in progress) → inserts a `running` row
   with `promptVersion` and returns the resume text and saved preferences.
3. `analyzeResume()` (`lib/analysis`) walks `getAIProviders()` (primary
   first): ask in JSON mode → validate with Zod → on failure ask once more with
   the validation errors → otherwise next provider. Request errors (rate
   limits, outages, 55 s timeout) go straight to the next provider.
4. Skill names: fixed alias map (`convex/skillNames.ts`) → `skillCache` in
   Convex → ESCO search (exact label/alt-label match only; cached either way).
   Career goals are merged with the saved preferences (user's choices first).
5. `analyses.complete` / `fail` (server secret) store the result. `result` is
   kept as the model returned it; `skills` starts as a copy and is what the
   user edits (`analyses.updateSkills`) and what matching uses. Every run is a
   new row, so earlier analyses remain as history.

## Job ingestion flow (Phase 4)

1. Convex cron (`convex/crons.ts`, daily 03:30 UTC) → `jobsCron.triggerSync`
   POSTs `${JOBS_SYNC_URL}/api/jobs/sync` with `x-jobs-sync-secret`. It does
   nothing until `JOBS_SYNC_URL` and `JOBS_SYNC_SECRET` are set on Convex
   (a Convex cloud deployment can't reach `localhost`, so locally run it by hand:
   `curl -X POST "localhost:3000/api/jobs/sync?force=1" -H "x-jobs-sync-secret: …"`).
2. Route: refuses runs less than 20 h apart unless `?force=1` (protects free
   quotas) → `syncJobs()` runs every adapter in `lib/jobs/sources/` (Adzuna and
   Jooble skip themselves without keys) → drops listings older than 30 days,
   non-tech titles, and in-run duplicates (`source:externalId`, title+company hash).
3. Level/type: keyword rules and source hints first; unclear listings that aren't
   labelled yet go to `getCheapProvider()` (Groq `GROQ_CLASSIFY_MODEL`), batched
   30 per request, at most 3 requests per run. Skills come from the alias map
   in `convex/skillNames.ts` (no AI), so they match resume skill names.
4. `jobs.upsertBatch` (server secret) inserts/refreshes; a title+company hash
   already stored from another source counts as a duplicate. `jobs.expireBatch`
   deletes rows posted > 30 days ago or not returned for 2 days by a source that
   synced fine. `jobs.recordRun` logs per-source call counts in `jobSyncRuns`.
5. `/jobs` lists and searches listings (`jobs.list`, `jobs.search`), each with
   a "via <source>" credit link (required by Remotive and Remote OK).

Per-run calls: Remotive 3, Himalayas ≤10, Remote OK 1, Arbeitnow ≤5,
Adzuna ≤4 (~120/month), Jooble 2, Groq ≤3. Check totals with
`npx convex run jobs:countBySource`.

## Matching flow (Phase 5)

1. Job embeddings: after each sync, `embedPendingJobs()` embeds listings with
   no `embeddedAt` (Gemini `gemini-embedding-001`, 768 dims, `RETRIEVAL_DOCUMENT`)
   in requests of 50 and stores them in `jobEmbeddings` (not on `jobs`, so job
   queries don't send vectors to the browser). The free tier allows 100 texts
   per minute; `embed()` waits out 429s within a time budget and the rest wait
   for the next run. Backfill: `POST /api/jobs/embed` with `x-jobs-sync-secret`.
2. Browser: `POST /api/matches/refresh` with the access token (automatically on
   `/matches` when `matches.mine` reports `stale`: newer analysis, edited
   skills or preferences, or a newer job sync).
3. Route: `matches.begin` runs as the user (latest done analysis, rate limit
   `matchRefresh`, one run at a time) → embeds the profile text
   (`RETRIEVAL_QUERY`) → `matches.recall` action (server secret): one
   unfiltered vector search (50) plus one filtered by preferred job types (30),
   hydrated through an internal query.
4. `rankCandidates()` (`lib/matching/score.ts`, pure):
   `0.45·semantic + 0.30·skill overlap + 0.25·preference fit − age penalty (≤ 0.1)`.
   Semantic stretches cosine 0.55–0.85 to 0–1; skill overlap uses canonical names
   from `convex/skillNames.ts`; preference fit weighs job type, level vs seniority,
   location (remote always fits) and role words in the title. Dismissed jobs are dropped.
5. `explainMatches()`: one batched AI call for the top 10 (reason + missing
   skills), Zod-validated, each provider tried once. If all fail, rule-based
   reasons are stored and the run is marked `explained: false`.
6. `matches.complete` (server secret) replaces the user's `matches` rows. The
   page reads them reactively (`matches.mine`); `matches.setFeedback` stores
   saved / applied / dismissed in `jobFeedback`.

## Hardening (Phase 7)

- **AI calls:** both providers go through `instrument()` (`lib/ai/telemetry.ts`):
  a per-attempt timeout (`AbortSignal`), retries on 429/5xx/timeouts
  (`lib/ai/retry.ts`, jittered exponential backoff capped at 10 s, or the
  server's Retry-After), and a telemetry record per attempt. Call sites pass
  `feature`, `timeoutMs` and `attempts` to fit their route's `maxDuration`.
  `withFallback` tries the primary once, then gives the fallback the retries.
- **Telemetry:** `recordAICall()` logs `{"event":"ai_call",…}` and writes an
  `aiCalls` row (server secret), fire and forget. Metadata only. A daily cron
  (`aiCalls.prune`) drops rows older than 30 days. `usage.myLimits` reads the
  rate-limit buckets without consuming; `usage.service` summarises `aiCalls`
  for `ADMIN_USER_IDS`. Both power `/usage`.
- **CSP:** `proxy.ts` makes a nonce per page request and sets the policy from
  `buildCsp()` (`lib/security/csp.ts`) on the request (Next.js applies the
  nonce to its scripts) and the response. The root layout passes `x-nonce` to
  the theme script. This makes every page dynamically rendered.
- **Tests:** `vitest.config.ts` has two projects. `convex` runs
  `convex/**/*.test.ts` in the edge runtime through `tests/convex.ts`, which
  registers the auth, username and rate-limiter components and creates real
  session rows. `unit` runs `lib/**/*.test.ts` and `tests/unit`. Playwright
  specs live in `tests/e2e`.

## Conventions

- One AI entry point: `getAIProvider()`. Features never import an SDK directly,
  so switching Gemini ↔ Groq is an env change (`AI_PROVIDER`).
- All AI output that we store is validated with a Zod schema first.
- One adapter per job source in `lib/jobs/`, all normalised to one `Job` shape.
- Read `convex/_generated/ai/guidelines.md` before writing Convex code, and
  `node_modules/next/dist/docs/` before writing Next.js code (v16 differs from
  older versions).
